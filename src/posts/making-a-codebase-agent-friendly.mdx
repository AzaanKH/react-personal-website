Using poteto-mode to make my [Fantasy Draft Assistant](https://github.com/AzaanKH/fantasy-draft-assistant) repo more agent friendly.
I was interested in the workflow that allows poteto to ship so much and be so productive. Setting it up was pretty easy: just download the repo and run `setup-pstack`. It asks some questions about the environment, and after they are answered pstack is set up.

So some information on my [Fantasy Draft Assistant](https://github.com/AzaanKH/fantasy-draft-assistant), it helped me draft my fantasy football team on Sleeper and ESPN for the 2026-2027 NFL season. To connect to Sleeper, just paste a link to the draft and the position you are drafting from here:

<Figure {...screens.connectSleeper} alt="The Live draft sync dialog over the draft board. Rules for this draft is set to Quick mock with default league rules, Draft provider is set to Sleeper, a Sleeper draft URL or ID field holds a sleeper.com draft link, and a Continue button sits below it." />

To connect to ESPN and Yahoo you must use the draft extension.

So the tool has a web app, a Chrome extension that is a side panel, a sync server, CLI and scripts to collect data for rankings. Most of it was written by coding agents, with me reviewing. There were issues that kept happening, so I decided to rebuild the codebase to break it up and bring correctness to the whole repo.

By October 2026 the agents kept making the same mistakes. A fix would land, and two PRs later a different agent would reintroduce the bug from a different file. The code looked right from the file the agent had open. It was wrong for the repo.

So I spent eight days rebuilding the codebase around one rule: a change that looks right from one file should be right for the whole repo, because the wrong version no longer compiles or lints. A team of agents did the work. This post covers how we found the problems, what changed, how the agents were organized, and what it cost.

## The problem was repetition, not any single bug

Agents can find out what code to use and what to do, however I discovered that draft order math lived in the mock draft engine, and the server, extension and CLI each had their own copy. Session state lived in each tab's store, in localStorage, in the React Query cache and on the server. There were four HTTP clients. Scoring was implemented three times. There was so much repeated work in the code, and knowing this I wanted to move to one single clean place where the helpers and abstractions live. This would make it so that there won't be any repetition in the repo.

I had been fixing this with instructions. `AGENTS.md` grew rules like "read the body inside the same tryPromise" and "build shared first". Agents read the rules, mostly. The bugs came back anyway.

## How we found the issues

Before just going in to change everything, I wanted to see exactly what goes wrong, and I used five evidence miners and three code explorers in parallel:

- One read the git history, 254 commits.
- One read the PR reviews: 71 PRs with 194 review findings and 28 CI failures.
- Three read my own messages in past agent sessions: 25 Claude Code chats, 276 Codex sessions and 28 T3 threads read in depth.
- Three explorers mapped how state, calculations and tooling actually worked.

## Prototype first, then plan

So with poteto-mode, to figure out what to do, it makes small throwaway prototypes to test what is possible. Each prototype ends with a verdict that is VERIFIED, NOT VERIFIED or INCONCLUSIVE.

<Figure wide {...diagrams.prototypeVerdicts} alt="Grid of prototype verdicts. P1 draft-order type change: verified, 17 sites flagged and 3 live bugs. P2 package extraction: verified, verify-time cost inconclusive. P3 lint replay: verified for four rules, not verified for sessionMode. P5 performance: derive verified, dedup gain not verified. P7 schema decoders: cost verified, parity not verified. P8 source condition: verified. P9 multi-tab persistence on a toy reducer: Web Lock verified, per-tab logs and IndexedDB not verified. Unit 0 in the installed extension: Web Lock not verified, IndexedDB verified with 9,000 of 9,000 commands kept." />

The NOT VERIFIED results were the most useful ones. They also show how the prototypes can improve the codebase, and what the impact is. Here are some examples:

**A lint rule cannot catch a missing check.** P3 replayed four candidate lint rules against the files as they were just before real past bug fixes. The rules for JSON casts, bare `fetch`, the snake-draft default and cross-package imports all fired on the buggy lines. A rule on `sessionMode` branches fired too, but on the wrong lines. The bug that `e362fc9` fixed was a `canDraft` check that was never written, and you cannot lint for an absence. That class needed an architecture change instead: one `canDraft` answer that every component reads.

**The obvious performance fix was worthless.** The recommendation board recomputes per position, so de-duplicating the shared scoring work looked like an easy win. P5 measured it at 0.01% to 0.90%, with identical outputs across 253 comparisons. The real cost was survival and lineup optimization, 20.7 ms at pick 100. That went on a separate list.

**The hand guards were looser than their own types.** P7 swapped three hand-written guards for Effect Schema decoders and compared them on the same inputs. Exact parity failed. In 6 of 7 differences the old guard accepted data that its own TypeScript type forbids. That is exactly the drift you get when a type and its guard are written separately.

**The toy test picked the wrong storage design.** P9 compared three multi-tab persistence designs on a toy reducer: per-tab logs, an IndexedDB transaction, and a Web Lock around one localStorage key. Across 37,800 stress commands, per-tab logs reversed 9 accepted decisions and lost an accepted pick. The Web Lock design had zero violations and the shortest code, so the plan chose it.

Then unit 0 ran the same harness inside the installed Chrome extension's side panel, against a real web app tab. The Web Lock design lost acknowledged commands in every granted-permission run, up to 170 of 3,000, including accepted picks. IndexedDB with re-reads on focus and visibility kept all 9,000. Plan Amendment 1 reversed the decision the same day. If we had skipped the spike, the multi-tab rewrite would have shipped the wrong design.

### Sequencing the work

When implementing, poteto-mode breaks the work into units and phases, with each phase getting a review to see its impact. If a phase causes bugs or issues, it works on those issues until it is ready to merge. So the plan split the work into units of at most 99 changed files each, ordered to test the riskiest unknown first and to delete code before adding it. Five landing units (1, 2, 3, 4 and 15) had no dependencies, and neither did the unit 0 spike, which never landed. The rest formed a chain.

<Figure wide {...diagrams.unitDependencies} alt="Dependency graph of plan units. Units 0, 1, 2, 3, 4 and 15 have no dependencies. Unit 3 feeds 4b and 5. Unit 4 feeds 5 and 9. Unit 5 feeds 6. Unit 6 feeds 7 and 13. Unit 7 feeds 8 and 14. Units 4b and 5 feed 10. Units 10 and 0 feed 11. Unit 11 feeds 12." />

Two choices in the order mattered most. The draft-order unit went third, because it fixed live bugs and every later unit used it. And unit 4b landed a test-only shadow of the new derived draft state right after it. Unit 4b replayed every existing store scenario through both the old and the new path before any production code switched over.

## The core idea: close each mistake class with structure

The plan ranked enforcement levels, highest first:

1. **Architecture.** There is one place the thing can happen.
2. **Type.** The wrong version does not compile.
3. **Lint or CI, with an error that names the fix.** The wrong version fails the gate, and the message tells the agent what to do instead.
4. **Test.**
5. **Docs.**

Each class got the highest level that worked, and docs were the last resort. The lint messages matter more than they look. An agent that hits `no-restricted-syntax` learns nothing. An agent that hits this message knows what to type next:

```js
{
	selector: "LogicalExpression[operator=/^(\\?\\?|\\|\\|)$/][right.value='snake']",
	message: 'No snake fallback. Use createSlotSequence with a required DraftFormat from @fantasy-draft/shared/draft, implemented in shared/src/draft-order.ts.',
},
```

New lint rules started with a baseline file. Existing violations went into `eslint-baseline.json`, and CI fails only when a count rises. P3 measured 108 existing sites across the first four rules, so an error-level rule on day one was not an option.

Most of the refactor follows one pattern. Find the thing that several modules each do for themselves, give it one owner, delete the copies, and make the copy impossible to write again.

### One draft order owner

So there is a mock draft, where a user doesn't need to connect to an outside source to draft. Before, the snake-only helper sat in the mock draft engine, next to the type-aware one:

```ts
// web-app/src/lib/mock-draft-engine.ts at 8f1d26a
export function getTeamIndexForPick(pickNumber: number, totalTeams: number): number {
	const roundNumber = Math.ceil(pickNumber / totalTeams);
	const pickInRound = ((pickNumber - 1) % totalTeams) + 1;
	return roundNumber % 2 === 1
		? pickInRound - 1
		: totalTeams - pickInRound;
}
```

`ProvisionalPickDialog` called the snake-only one. In a linear draft, even round picks showed the wrong team and could not be saved. `DraftDecisionBar` and `SidePanelPage` computed "picks until your turn" with snake order too. P1 found all three by making `draftType` required and deleting the snake helper. The compiler flagged 17 production sites, and three of them were live bugs.

### One command path

Draft commands used to go straight into writable module singleton stores. Any file could import a store and mutate it. This should be centralized, where one place owns the commands and everything sends its commands there. #99 created one workspace at the browser composition root. UI, sync, CPU, queue and connection callers send typed commands to it, and the singleton APIs are gone.

UI code now reaches storage through one function. When IndexedDB is on (#117), the same call goes through the durable path:

```ts
// web-app/src/workspace/ui-dispatch.ts on main
export function dispatchWorkspace(workspace: Workspace, ...command: VoidWorkspaceCommand): void {
	if (STORAGE_ACTIVATION_ENABLED && workspace.sendDurable) {
		void workspace.sendDurable(command).catch(() => undefined);
	} else workspace.send(...command);
}
```

### A derived DraftView instead of stored fields

The old store held `draftedPlayerIds`, `teamRosters`, `myRoster` and `currentPick` as stored fields, and a hand-written rebuild ran after every change:

```ts

	state.draftHistory.sort((left, right) => left.pickNumber - right.pickNumber);
	// …
	state.draftedPlayerIds = new Set([
		...state.draftHistory.map((pick) => pick.playerId),
		...effectiveKeepers.map((keeper) => keeper.playerId),

	rebuildCanonicalRosters(state);
	state.currentPick = getNextCanonicalOpenPick(/* … */);

```

There were five or more of these rebuild blocks. Miss one, and a field goes stale.

	readonly available: readonly Player[];

	readonly canRecord: boolean;
	// …
}

<Figure wide {...diagrams.ownDraftView} alt="Before and after diagram for derived state. Before: draftedPlayerIds, teamRosters, myRoster, currentPick and isMyTurn are stored and rebuilt by hand. After: the board, player pool, permissions and recommendations all read from deriveDraft." />

This was the riskiest switch, so it went in four steps (#94 to #97). The shadow replay found 109 cursor and turn differences first: the old store could hold cursor 1 or cursor 96 for identical facts. So #94 added the missing progress facts before any reader switched. By #95 the shadow matched 111 scenarios and 1,151 states with zero differences. A full derive, including the 600-player pool and permissions, costs 0.221 ms at 139 picks.

`canDraft` on the derived view is also the fix for the class P3 could not lint. There is one answer to "can I draft this player?", and components read it.

### One persistence layer

This was the biggest unit and the one that went wrong the most.

Before, each tab and the side panel did a compare-then-write to the same localStorage key, with a single-slot journal for unconfirmed saves. #98 built a real app browser harness and measured the old path: with two tabs under contention, 3,893 of 9,000 acknowledged effects were missing after reload. With the installed extension, 3,589 were missing. That bug was on main.

<Figure wide {...diagrams.ownPersistence} alt="Before and after diagram for persistence. Before: two tab stores and the extension side panel each compare-then-write localStorage, plus a single-slot journal and the React Query cache. After: tabs and the side panel commit through one IndexedDB readwrite transaction, and old v1 tabs honor a tombstone and stop writing." />

After the unit 0 spike, the design is an IndexedDB readwrite transaction with strict durability. Each command reads the latest record, applies the reducer and writes, all in one transaction. Other tabs re-read on a BroadcastChannel message, on focus and on visibility change. There is no Web Lock in the final design. The spike ruled it out.

The whole contract fits in one function. It checks the migration fence, reads, applies, decodes and writes, all inside one readwrite transaction:

```ts
// web-app/src/workspace/indexed-db.ts on main (excerpt)
update: (identity, apply) => transaction(['sessions', 'metadata'], 'readwrite', (tx, done, abort) => {
	const store = tx.objectStore('sessions');
	const fence = tx.objectStore('metadata').get(ACTIVATION_RECORD);
	fence.onsuccess = () => {
		if (writersStopped(fence.result)) { abort(new DraftWritersStoppedError()); return; }
		const get = store.get(sessionKey(identity));
		get.onsuccess = () => {
			try {
				const previous = readSession(get.result);
				const next = apply(previous);
				const session = decode(next.session);
				// … identity check …
				if (JSON.stringify(session) !== JSON.stringify(previous)) store.put(session, sessionKey(identity));
				done({ session, result: next.result });
			} catch (error) { abort(error); }
		};
	};
}),
```

Shipping it took six PRs:

- #102 made old v1 writers honor a migration tombstone. When the tombstone exists, an old tab stops writing and shows the existing reload flow. Its data stays.
- #103 added the IndexedDB store and the v1 importer, switched off.
- #104 added the activation path behind a build switch that defaulted to off, plus a rollback export to v1 bytes.
- #117 turned IndexedDB on by default. `VITE_STORAGE_ACTIVATION=v1 pnpm build` still produces the rollback build.
- #118 and #119 closed review follow-ups: a slow-storage notice, and conflict tests with activation on.

An earlier change taught us a rule the hard way. The first head of #95 bumped the session record version. Older tabs, including the deployed main, rejected the record, reset history and wrote it back, which erased manual picks. The verifier blocked it. Amendment 7 now requires every persisted change to be additive, and the PR must prove that real old modules from main load and rewrite the new bytes without loss.

### One HTTP runner and one process runner

There were four HTTP clients and three spawn-and-kill implementations. Retry-After handling was redone three times. A process-cleanup fix was reversed. The lessons lived in `AGENTS.md` as prose.

Before, the extension's snapshot client did its own body cancel, JSON parse and timeout:

```ts

	// Cancel the unread body; the timeout cannot abort it once this rejects.

const parsed: unknown = await response.json();
```

After #90, it calls the shared runner, and a decoder and a timeout are required arguments:

```ts

return await http.json(url, parsed => {
	try { return decodeDraftSyncSnapshot(parsed); }
	catch (cause) { throw new Error('Sync server returned an invalid draft snapshot', { cause }); }
}, { timeoutMs: requestTimeoutMs, retries: 0, retryAfter: true }, {
	fetch: fetchImplementation, init: { ...init, signal },

```

### One owner for slot and provider identity

"Which draft slot is mine" lived in several places: the connection store, the draft store config, the URL, extension storage, and an effect that copied one into another. A stale connection could overwrite a later user choice on reload.

<Figure wide {...diagrams.ownSlotProvider} alt="Before and after diagram for slot identity. Before: the connection store, draft store config, an effect mirror, the draft URL and extension storage each hold a slot value. After: workspace draft state is the only writer, and the URL, extension and provider values are hints." />

After #105, workspace draft state is the only owner. The URL, the extension and the provider are hints, applied through workspace commands with an explicit precedence. The saved slot and a later user choice win, and a foreign draft URL position is ignored.

## The agent workflow

<Figure wide {...diagrams.agentTopology} alt="Topology diagram. The operator approves and lands. The root orchestrator writes briefs, verdicts and the decision log, and is the only writer of the stack topology. It sends briefs to unit owners, PRs to read-only verifiers, and run authorizations to GPT browser runners." />

### Roles

- **Me, the operator.** I approved the plan, answered product questions (decoder strictness, the season rule, where private data lives, the IndexedDB rollout), and landed the stack.
- **The root orchestrator.** One Claude session. It wrote each unit's brief with a base SHA, launched owners, posted one verdict comment per PR, restacked branches, and logged every decision to `decisions.tsv`. It was the only agent allowed to change the stack's shape.
- **Unit owners.** Codex `gpt-6.1-sol` on high reasoning effort, one worktree and one branch each. Owners could force-push only their own branch and never merge or retarget. Opus owners took the UI units and stepped in when Codex hit its usage limit. Every owner ended with one self-contained report and the word `STACK-READY`, or what blocked it.
- **Verifiers.** Sonnet, read-only, doing code, diff and byte checks. Later, Codex became the default reviewer and Sonnet did only each unit's final review.
- **Browser runners.** Every browser task ran on Codex GPT models: Playwright stress matrices, smoke tests, pixel comparisons and the UI walkthrough later in this post.

Planning used the same split. Two architects, Opus and GPT, each designed the target architecture twice, and a GPT cross-judge scored the candidates 20/25 against 11/25. The plan took the winning candidate as its base and grafted in ideas from the other, each tied to a prototype receipt. I also used `gpt-6.1-sol` for verification, checking the code impact, and eventually added the [sol-loop skill](https://github.com/t3dotgg/tstack/blob/main/skills/sol-loop/SKILL.md) from tstack. I always use Sol to verify changes, and this skill is a great way to also get pushback and get the most out of the review.

### Stacked PRs and the landing order

Every unit was one link in a single PR stack: #76 on main, #77 on #76, and so on. Each PR stayed under 100 changed files and stayed reviewable on its own diff. The cost is that every change near the bottom means restacking everything above it.

<Figure wide {...diagrams.prTimeline} alt="Timeline of 45 PRs from #76 to #120. Owners opened PRs steadily from October 18 to October 26. #76 to #103 merged together on October 23, and #104 to #120 merged together on October 26. Fifteen Codex usage-limit stops are marked along the bottom." />

I landed #76 to #103 on October 23. On the evening of October 25, Pacific time, I asked the root to merge #104 to #120. Those merges are dated October 26 in UTC. Two PRs, #92 and #101, were copies of fixes aimed at main, and later stack PRs made them unnecessary.

### Tiered testing

The persistence units ran the full browser stress matrix again and again, 9,000 commands per scenario. It drained usage fast. On October 22 I changed the policy to escalate only when a cheaper tier gives a reason to.

<Figure wide {...diagrams.testingTiers} alt="Pyramid with three tiers. Tier 1, deterministic unit tests in jsdom and fake-indexeddb, runs on every commit in seconds. Tier 2, one GPT browser smoke per persistence PR, runs 300 commands per actor plus 20 conflicts and 20 moves. Tier 3, the full 9,000-command matrix, runs only if a lower tier fails, the write path changes, or before a production flip." />

<Callout title="The rule that made this work">

Every stress failure is first turned into a Tier 1 test that fails before the fix. After that, the expensive tier only has to confirm.

Tier 3 still paid for itself on the flip. On #117 it caught a real bug. ### Usage and cost

I ran out of quota a lot. The decision log records 15 times an owner stopped on a Codex usage limit or capacity error. The early evidence miners all hit a Claude session limit at once and had to wait for the reset.

Here is what I learned about cost, mostly about the root agent:

- **Every wake re-reads the root's whole context.** Bot comments from CodeRabbit and Cloudflare, duplicate notifications and owner progress messages each woke the root for nothing. One retired root thread had 1,503 items when it was retired. At that size every wake was expensive.
- **Owners report once.** I changed the owner brief so owners send one final report and message the root earlier only for a decision. No progress check-ins.
- **Wait for CI in a background job, not a PR watch.**
- **Send large reads to a subagent.** Anything over about 5k tokens goes to a subagent that returns a short verdict.
- **Rotate the root when its thread is too long, not when a phase ends.** I retired two root threads for usage. Both should have been retired well before they reached 1,200 items. A fresh root picked up from `HANDOFF.md` without losing state.
- **One review round by default,** and browser work on GPT, not Claude.

### What went wrong

**Usage limits.** When Codex ran out mid unit, the root waited for the reset and resumed the same owner thread, so the owner kept its context. Sometimes T3 resumed the owner automatically, so the root learned to check before sending a resume and starting a duplicate run. When an owner stopped right after opening its PR, the root verified the PR with an independent verifier instead of starting a new owner.

**Restacks.** Fixes near the bottom of the stack meant rebasing every PR above. Two stacks (docs and gates, and tokens and skeletons) both grew from #108 and edited the same lint files, so the second needed a rebase and a baseline format conversion.

**CI audit failures.** Two dependency advisories (Vite and Vitest) appeared mid stack. Every stack PR from before the bumps fails CI's audit step if rerun. The fix was a bump PR on main plus a copy at the top of the stack (#93, #100). Once, CI audit socket timeouts needed two reruns before #101 and #102 went green.

**A flaky host.** One Tier 3 run on the flip PR failed at 18% battery. The log showed the laptop had gone to idle sleep for 29 seconds. The rerun used AC power and `caffeinate`.

**The landing itself.** The root merged the second batch top-down with merges pinned to verified SHAs. GitHub refused every second PR, because merging a child into its parent changed the parent's head. Consolidation PR #120 carried the verified tip into #104's branch, and the tree on main matched the verified head. For next time: re-read each parent's head right before merging, or land the stack through one PR.

### Two process lessons

A laptop going to sleep cost me a run for the second time. After the first fixes, the headless browser gate failed 2 checks on the branch and passed on main. An agent read the `pmset` logs and found that the Mac had gone into idle sleep during that one run, which took 10 minutes instead of about 30 seconds. Rate limits hit mid-run again. The first agent finished all four groups before a limit cut it off. Its replacement was briefed as if no code existed yet. It was cancelled before it could overwrite the work. Before I re-brief an agent now, I check the state of the branch.

## What I'd do differently

**Spike the real environment before trusting the toy.** P9's toy prototype picked the wrong storage design with zero violations. The installed extension behaved differently. I now run the riskiest prototype in the real runtime first, even when it is slower to set up.

**Set the testing tiers on day one.** Tiered testing came on day five, after repeated full matrices had drained usage. Each Tier 3 run took hours. A rule that every failure becomes a Tier 1 test first would have saved most of that.

**Keep the root small from the start.** The biggest avoidable cost was a root thread that grew past 1,500 items while bots and owners woke it. Final-report-only owners, background CI waits and a size rule for reads should have been in the first brief, not added on day eight.

**Do a user walkthrough per UI-facing PR, not after the stack.** The storage setup screen passed every functional gate. A short screenshot pass on #104 would have caught that it was the first thing new users see.

**Plan the landing, not just the stack.** Merging 40 stacked PRs is its own task. Pinned top-down merges failed in a way I had not predicted. Next time I land through one consolidation PR from the start, or re-read each parent's head right before its merge.

**Write the decision log from the first minute.** This is the one thing I would keep exactly as it was. Every number in this post traces back to `decisions.tsv`, a PR body, or a receipt, because the root logged each decision with its evidence as it went.
